## Context

`add-quadmemo-quadrant-ui` により、メモ画面・入力バー・コミットパイプライン（`tokenize` → `resolvePlacement` → `addChips`）と Zustand ストア（`addChips` / `moveChip` / `editChip` / `removeChip` / `clearAll`）が揃っている。`resolvePlacement` は常に既定象限を返すスタブで、状態はメモリ上のみ。

動機は proposal.md - Why を参照。要求の原本は specs/word-classification/spec.md と specs/memo-persistence/spec.md。技術選定（`idb`、`Intl.Segmenter`、Vitest）は仕様書 §4、正規化・マッチング規則は §7、データモデルは §8 に従う。

## Goals / Non-Goals

**Goals:**

- 正規化・マッチング規則をユニットテストで固定し、以後の change が壊したら即座に落ちる状態にする（仕様書 §7.4）
- 永続化を Zustand アクションの内側に閉じ込め、コンポーネントから DB を意識させない
- 保存失敗・保存不可という「静かに壊れる」経路を、利用者に見える失敗として扱う

**Non-Goals:**

- 辞書・設定の編集 UI とエクスポート/インポート（`add-quadmemo-dictionaries`）
- 既存チップの再分類（仕様書 §5.2 のとおり辞書変更では再分類しない。規則自体は `add-quadmemo-dictionaries` の `dictionary-management` で定義する）
- スキーマ v2 以降のマイグレーション（v1 のみ）
- 形態素解析による複合語の分割改善（仕様書 §7.1 のとおり辞書登録の運用でカバー）

## Decisions

### D1: 分類は `src/core/` の純粋関数、辞書は正規化済みキャッシュを渡す

```ts
// src/core/classify.ts
classify(token: string, dicts: NormalizedDicts, partialMatch: boolean): ClassifyResult
```

- 辞書は「正規化済みエントリ + 原文」の組をあらかじめ持つ形（`NormalizedDicts`）で渡す。正規化はロード時とデータ更新時に 1 回だけ行い、コミットごとには行わない
- `classify` は DB もストアも参照しない。これにより spec の「分類処理の決定性」が構造的に保証され、ユニットテストが表引きだけで書ける
- **代替案**: 辞書を DB から都度読む（コミットのたびに非同期 I/O が入り、決定性とテスト容易性を失う）

### D2: 完全一致は Map 引き、部分一致のみ線形走査

- 完全一致（既定モード）は `Map<normalizedEntry, {quadrant, raw}[]>` で O(1) に引く。同一エントリが複数象限にある場合は、最長一致は自明（長さが同じ）なので象限優先順で決める
- 部分一致モードのみ全エントリの線形走査を行う。仕様書 §7.3 の擬似コードと同じ結果になることをユニットテストで担保する
- **理由**: 辞書が数百〜千語に育ってもコミットの体感を落とさない。部分一致は既定 OFF なので線形でも実害が小さい
- **注意**: 最長一致の判定は「正規化後のエントリ長」で行う（原文の長さではない）
- **規則の効き方の整理**: 完全一致モードでは一致したエントリの正規化後長は必ずトークン長と等しくなるため、最長一致規則が結果を分けるのは**部分一致モードのみ**である。完全一致モードで複数象限が競合するのは「異なる原文が同じ正規化結果になる」場合（例: `レビュー` と `れびゅー`）で、この場合は同長の競合として象限優先順で決まる。test-plan の fixture はこの区別に沿って用意する

### D3: 正規化はカタカナ→ひらがなのコードポイント演算

仕様書 §7.2 の実装（`NFKC` → `toLowerCase` → `ァ-ヶ` を `-0x60` シフト → `trim`）をそのまま採る。長音符・漢字かなのゆらぎは吸収しない。

- **順序が重要**: `NFKC` を先に適用しないと半角カタカナが変換対象にならない。この順序をユニットテストで固定する
- **`toLowerCase` の位置**: NFKC の後、かな変換の前。トルコ語ロケール等の影響を避けるため引数なしの `toLowerCase()` を使う（`toLocaleLowerCase` は使わない）

### D4: IndexedDB は `idb` ラッパー、DB `quadmemo` v1、3 ストア

| ストア | keyPath | インデックス |
|--------|---------|--------------|
| `memos` | `id` | `quadrant`、`createdAt` |
| `dictionaries` | `quadrant` | - |
| `settings` | `key` | - |

- `src/db/schema.ts` に型定義・`openDB`・`upgrade`（v1 のストア作成とシード投入）を置く
- `src/db/repository.ts` に CRUD を置き、ストアからのみ呼ぶ
- **シードは `upgrade` 内ではなく起動時のロード処理で行う**: `upgrade` トランザクション内で長い処理をすると失敗時の切り分けが難しく、また「既存データがあれば上書きしない」判定はストアが空かどうかで素直に書ける

### D5: 識別子は ULID、`ulid` パッケージを採用

- **採用**: `ulid` パッケージの `monotonicFactory()` を使う
- **理由**: 同一ミリ秒内の連続コミット（1 コミットで最大 50 件生成される）でも単調増加が保証され、`createdAt` が同値でも並び順が決まる。自前実装だと Crockford Base32 と単調性の実装を持つことになる
- **代替案**: `crypto.randomUUID()`（時系列ソート不可のため、`createdAt` 同値時の順序が不定になる）

### D6: 保存は楽観的更新 + 1 回リトライ + 失敗の可視化

```
addChips → ストアへ即反映（UI 表示）→ 永続化を試行
                                   ├ 成功: 何もしない
                                   └ 失敗: 1 回リトライ → なお失敗ならチップに unsaved フラグ + エラートースト
```

- **理由**: コミットは連続発話中に走るため、DB 書き込みを待つと入力が詰まる。仕様書 §11 の「チップは画面に残しリトライ（1 回）」に一致する
- **`unsaved` フラグは永続化対象ではない**（保存できていないので当然）。リロードすると消えるが、それは「保存されていなかった」という事実の正しい反映
- **移動・編集・削除も同じ扱い**にする。削除が保存できなかった場合はリロードで復活するため、削除失敗時も同じ経路でエラー通知する

### D7: 保存可否の判定は probe 書き込みで行う

`indexedDB` の存在チェックだけでは不十分（プライベートモードでは open できても書き込みで失敗する実装がある）。起動時に `settings` ストアへ probe レコードを書いて読み戻し、例外・不整合があれば「保存できない環境」と判定して案内を出す。

- **トレードオフ**: 起動時に 1 往復の I/O が増える。初期ロード 1 秒以内（仕様書 §12）の予算内に収まる軽量な操作に留める
- 案内はメモ画面上部の常設バナーとし、閉じても再訪時に再表示する（保存できないという状態は継続しているため）

### D8: `navigator.storage.persist()` の結果はストアに保持し、表示は次 change

起動時に一度だけ要求し、結果（`granted` / `denied` / `unsupported`）をストアに保持する。設定画面での表示は `add-quadmemo-dictionaries` で行う。E2E からは観測しづらいため、検証はユニットテストと実機確認に委譲する（test-plan 参照）。

### D9: 設定値は本 change では読み取り専用、E2E は fixture で与える

`partialMatch` / `allowDuplicates` / `autoCommitMs` / `showDictationHint` は `settings` ストアから読むが、変更 UI は `add-quadmemo-dictionaries` で追加する。したがって部分一致・重複抑止の E2E は、fixture が IndexedDB へ直接設定値を書いた状態から始める（fixture 直接方式。`add-quadmemo-quadrant-ui` design - D10 と同じ理由）。

### D10: 外部送信ゼロは E2E のネットワーク監視で担保する

配信元オリジン以外へのリクエストが 1 件も出ないことを Playwright のリクエスト監視で検証する。解析ライブラリを将来うっかり足したときに落ちるガードとして機能させる。

## Risks / Trade-offs

- **正規化の順序ミスで半角カタカナが一致しない** → D3 の順序をユニットテストで固定（半角カタカナ・全角英数・カタカナ・ひらがなの 4 系統を必ずテストする）
- **最長一致を原文長で判定してしまう** → 正規化後長で判定するテストケース（正規化で長さが変わる全角英数など）を置く
- **楽観的更新により「画面にあるのに保存されていない」状態が生まれる** → `unsaved` の可視化を必須にし、E2E で警告表示を検証する
- **保存失敗の注入が難しくテストが書きにくい** → fixture でリポジトリの書き込みを失敗させる注入口（`window` 経由のテストフック）を用意する。テストフックは本番コードに残るため、`import.meta.env.DEV` などでガードせず**常時有効にする代わりに副作用のない読み取り専用フックにする**（フラグを立てるだけ）
- **iOS のストレージ削除リスク**（長期未使用でデータが失われる） → 仕様書 §8.4 のとおりエクスポートをバックアップ手段として位置づける。本 change では `persist()` 要求までを行い、バックアップ機能は次 change
- **1 コミット 50 件の一括書き込み** → `memos` への書き込みは 1 トランザクションでまとめる（部分成功による中途半端な状態を避ける）
- **DB スキーマを後の change で変えたくなる** → 型定義は仕様書 §8.2 のとおりに置き、`schemaVersion` を持つエクスポート形式（§8.3）を次 change で導入することで、将来の移行余地を残す

## Migration Plan

新規 DB のため移行なし。ロールバック時（本 change を戻す場合）は IndexedDB `quadmemo` が残るが、`add-quadmemo-quadrant-ui` のコードは DB を読まないため無害。
