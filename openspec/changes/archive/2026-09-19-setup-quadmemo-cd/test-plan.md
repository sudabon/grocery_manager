# Test Plan

specs/ 配下の全シナリオ（continuous-deployment 9 件・static-hosting 4 件）を、E2E で検証可能な観点へ翻訳したもの。
受け入れ基準の原本は spec のシナリオであり、本ファイルで新しい仕様は定義しない。

前提:

- 本 change の E2E は **配信済みの CloudFront 配信ドメイン** に対して実行する。既存の `env:deployed-origin` fixture（`E2E_BASE_URL` が HTTPS の配信ドメインでなければ skip）を使う
- 本 change の E2E は **CD が 1 回以上完走した後** に意味を持つ。ローカル開発サーバーに対しては実行対象外
- 「配信されている内容が既定ブランチと一致する」ことは、配信中のアプリシェルが参照するハッシュ付きアセットと、手元のビルド成果物が参照するそれとの一致で観測する。CD はビルドからアップロードまでを一続きで行うため、両者が一致することが「マージした内容が配信に到達した」ことの観測可能な形になる
- 配信の契機・資格情報・直列化はいずれもブラウザから観測できない。これらはワークフロー定義・Terraform コード・`deploy.sh` の単体テスト・実運用での確認へ委譲する（下表）

## E2E観点一覧

| TP-ID | 対応シナリオ | 前提(fixture) | 操作の意図 | 期待結果 | リスク |
|-------|-------------|---------------|-----------|---------|--------|
| TP-001 | 既定ブランチへの統合を契機とした自動配信 / 既定ブランチへのマージで配信まで到達する、デプロイによる更新反映 / デプロイ後にリロードで新バージョンが反映される | `env:deployed-origin` + `env:current-build` | CD 完走後に配信ドメインのアプリシェルを取得し、手元のビルド成果物のアプリシェルと突き合わせる | 配信中のアプリシェルが参照するハッシュ付きアセットの集合が、手元のビルド成果物のそれと一致する | 高 |

### 異常系・境界の検討結果

- **異常系（検証失敗・ビルド不正）**: 配信が「実行されない」ことの確認であり、配信ドメインからは「内容が変わらない」としか観測できない。変更前後の同一性だけでは「CD が止まった」のか「CD が走って同じ内容を配信した」のかを区別できないため E2E には置かず、`deploy.sh` の単体テストとワークフロー定義のレビューへ委譲する（下表）
- **権限境界（資格情報の範囲・別ブランチからの取得拒否）**: IAM とワークフローの設定に対する検証であり、配信ドメインへの HTTP 要求からは観測できない。Terraform コードレビューと AWS CLI での実地確認へ委譲する（下表）
- **多重送信（連続マージ時の直列化）**: 2 回の配信を意図的に重ねる必要があり、E2E から AWS への副作用を起こすことになる。ワークフローの `concurrency` 設定のレビューと実行履歴の確認へ委譲する（下表）
- **空データ**: 配信物が空になるケースは `deploy.sh` の既存ガードが書き込み前に中止する。単体テストで固定済み（下表）。E2E としては TP-001 が失敗として検出する

## E2E対象外(委譲先と理由)

| シナリオ | 委譲先 | 理由 |
|---------|--------|------|
| 既定ブランチへの統合を契機とした自動配信 / 変更提案では配信が実行されない | ワークフロー定義のレビュー（`deploy.yml` の `on` が `push: branches: [main]` のみであること）＋ 変更提案作成時の実行履歴確認 | 配信が「起動しないこと」の確認であり、配信ドメイン側に観測できる変化が生じない |
| 検証を通過しない変更を配信しない / 検証の失敗で配信が行われない | ワークフロー定義のレビュー（deploy ジョブの `needs` に verify が含まれること）＋ 実行履歴確認 | ジョブ間の依存関係の検証であり、配信ドメインからは観測できない。意図的に検証を失敗させる変更を main へ入れることもできない |
| 検証を通過しない変更を配信しない / ビルド成果物が不正なら書き込み前に中止する | `tests/scripts/deploy.test.mjs`（既存の `aws` スタブで、中止時に `aws` が一度も呼ばれないことを確認） | オリジンへ書き込む前の中止を観測するには AWS 呼び出しの有無を見る必要があり、単体テストの守備範囲 |
| 配信に用いる資格情報の制約 / 長期アクセスキーを保持しない | リポジトリ設定の確認（Actions secrets に AWS の長期キーが無いこと）＋ ワークフロー定義のレビュー（`permissions: id-token: write` と `configure-aws-credentials` の `role-to-assume` を使うこと） | 資格情報の持ち方に対する検証であり、配信結果からは観測できない |
| 配信に用いる資格情報の制約 / 権限が配信先の外へ及ばない | Terraform コードレビュー（`infra/github_oidc.tf` のポリシーが 2 リソース ARN に限定されていること）＋ AWS CLI での実地確認 | IAM ポリシーの範囲の検証であり、E2E の対象外。design.md - D6 の対応表を基準にする |
| 既定ブランチ以外からの配信資格情報の取得の拒否 / 別ブランチからは配信資格情報を取得できない | Terraform コードレビュー（信頼ポリシーの `sub` 完全一致）＋ GitHub Environment の deployment branch 制限の設定確認 | 認証の拒否を E2E から起こすには、別ブランチでワークフローを実行する必要がある。design.md - D3 の三重化された制限を設定として確認する |
| 配信の直列化 / 連続したマージで配信が直列に実行される | ワークフロー定義のレビュー（`concurrency.group` が固定で `cancel-in-progress: false`）＋ 実行履歴確認 | 2 つの配信を意図的に重ねる必要があり、E2E から AWS へ副作用を起こすことになる |
| 配信の直列化 / 直列化の結果として最新の内容が配信される | ワークフロー定義のレビュー（deploy ジョブが契機となった SHA をチェックアウトし、その場でビルドすること） | 待機の前後で内容が変わる状況を E2E で作り出せない。最終的な配信内容の一致は TP-001 が担保する |
| デプロイによる更新反映 / 削除されたファイルが配信から消える | `tests/scripts/deploy.test.mjs`（既存の `--delete` 同期と不在エントリポイントの `rm` の検証） | 前回ビルドのハッシュ付きアセット名を E2E 側が知り得ないため、配信ドメインからは検証できない |
| デプロイによる更新反映 / 明示的に与えられた配信先が使われる | `tests/scripts/deploy.test.mjs`（環境変数を与えたとき `terraform` が一度も呼ばれず、与えた値が `aws` の引数に現れることを確認） | 配信先の解決経路の検証であり、配信結果は経路によらず同一。外形からは区別できない |
| デプロイによる更新反映 / 形式が不正な配信先ではデプロイが中止される | `tests/scripts/deploy.test.mjs`（不正な値を与えたとき非 0 終了し、`aws` が一度も呼ばれないことを確認） | 異常系の中止であり、正常な配信先には何の変化も起きない |

## タグ対応

- すべての実装テストに `@setup-quadmemo-cd` と `@TP-NNN` を付与すること
- 新規 fixture `env:current-build` を `tests/e2e/fixtures/README.md` に登録すること（`dist/index.html` が存在しない場合は `test.skip` し、存在すればアプリシェルが参照するハッシュ付きアセットのパス一覧を提供する fixture）
- 既存 fixture `env:deployed-origin` は登録済みのため追記不要
