## Context

- コミット制御は `useCommitController`（add-quadmemo-quadrant-ui D4）に集約されている。入力ごとにタイマーを張り直し、composition 中は抑止し、確定・Enter・クローズで即時コミットする
- iOS のディクテーションは composition イベントを出さない（WebKit bug 261764）。実機で `?debug` の一時計測（入力欄の `beforeinput` / `input` / `keydown` / `blur` と、React の `onChange`・コミットを時系列で記録）を行い、次の事実を得た
  - 話している間: `insertText` で途中結果が届き、更新は既存の途中結果を選択範囲にした置換（`sel=0-3` など）で来る
  - 自動コミットが入力欄を空にした後: 途中結果の更新が止まる（その後の発話は届かない）
  - 発話の区切りで: 「コミット時点の文字列 + その後の発話」が、空の入力欄へ選択範囲なしの `insertText` で語ごとに一気に書き戻される（英語 `You` / ` ` / `knew` / ` ` / `Tamargo`、日本語 `牛乳、` / `卵`）
  - 書き戻しのタイミングはコミットの 2.6 秒後〜15 秒後と不定で、次の発話の後に来ることもある
- Playwright は OS のディクテーションを起動できない。`fill` は「全選択 → `insertText`」なので、空の入力欄に対しては書き戻しと同じ形（選択範囲なしの `insertText`）になり、再現に使える

## Goals / Non-Goals

**Goals:**

- 書き戻しによる二重登録をなくす。書き戻しに続きの発話が含まれる場合は続きを落とさない
- spec「コミット後は入力欄をクリアしなければならない」を維持する
- キーボード入力・PC・Android など書き戻しが起きない環境の振る舞いを変えない

**Non-Goals:**

- 途中結果と確定結果の表記が異なる場合の吸収（D4 の割り切りのまま）
- ディクテーション中の自動コミットを抑止すること（ディクテーションを検出する手段がない）

## Decisions

### D1: コミット時点の表示文字列を「書き戻されうる文字列」として記憶し、先頭一致を除いた残りをコミットする

- **採用**: `useCommitController` で表示テキスト（入力欄の value）とコミット対象テキストを分ける。コミット時に表示テキストを `echo` として記憶し、以後の入力が `echo` で始まるなら `echo` を除いた残りをコミット対象にする。表示は入力欄の value のままにし、次のコミット（タイマーまたは手動）で空にする
- **理由**: 書き戻しは通常の `insertText` で届き、イベント種別・時間では区別できない。区別できる唯一の手がかりが「コミット時点の文字列で始まる」という内容の構造であり、採取した全ログでこの構造だった
- **表示を書き換えない理由**: 書き戻しは複数の `input` イベントで一気に届く。その途中で DOM の value を書き換えると、続く挿入位置がずれ、React の制御コンポーネントとの整合も崩れる（計測コードで実際に踏んだ）。表示は OS に任せ、コミット対象だけを計算する
- **`echo` の更新**: コミットのたびに「その時点の表示文字列」で上書きする。書き戻し後のコミット（残りをコミットしたとき）では表示文字列が OS の見ている累積の文字列になるので、以後さらに累積で書き戻された場合も先頭一致で除ける
- **不採用: 入力欄を空にせずコミット済みの長さを覚える**: spec「コミット後は入力欄をクリア」に反する。手入力と混在すると、既にコミットした文字列の上に打ち込む形になり崩れる
- **不採用: `beforeinput` の `inputType` で判別**: 書き戻しは `insertText` で来る。空の `inputType` で来る語もあるが一貫しない

### D2: 書き戻しが来ない契機で `echo` を捨てる

`echo` を持ち続けると、先頭が一致するだけの新しい入力（`卵` の後の `卵焼き`）を削ってしまう。次の 3 つでは書き戻しが来ないので `echo` を捨てる:

1. **`blur`**: フォーカスが外れるとディクテーションは終わる。バーを閉じる操作は「コミット → blur」の順なので、閉じた後は必ず捨てられる
2. **`keydown`**: キー入力は書き戻されない。ディクテーションは `keydown` を出さない（ログで確認）
3. **選択範囲を持つ `beforeinput`**: 途中結果を範囲置換で更新しているのは、OS がライブに入力欄を追跡できている証拠。入力欄が空にされた後は範囲置換は来ない（ログで確認）ので、これが来たら新しいフレーズであり、古い `echo` は不要。React 18 の `onBeforeInput` は native の `beforeinput` ではなく `textInput` 由来のポリフィルなので、`useEffect` で native のリスナーを付ける

### D3: 検証は単体テスト + `fill` による E2E + 実機ログ

- 先頭一致の除去・`reset` の効果は `useCommitController` の単体テストで固定する
- 3 つの契機の配線は `InputBar` の単体テストで固定する（選択範囲あり／なしの `beforeinput` を両方置き、範囲置換だけが `echo` を捨てることを示す）
- E2E は `fill` で書き戻しを再現し、chromium と mobile-safari で走らせる。修正前のコードで TP-001 / TP-002 が失敗することを確認済み
- 実機（iPhone / 日本語ディクテーション）では、修正後に `COMMIT "牛乳"` → 書き戻し `牛乳、卵` → `COMMIT "、卵"` となり、チップが 牛乳・卵 の 2 つだけになることを確認済み

## Risks / Trade-offs

- **同じ 1 語をすぐ続けて 2 回言う**: 1 回目のフレーズが（マイクを止めるなどで）コミット前に確定し、`echo` が残ったまま同じ語が新しいフレーズとして届くと吸収される。範囲置換が 1 度でも来れば `echo` は捨てられるので、2 語以上のフレーズでは起きない。買い出しメモで同じ語を直後に繰り返す場面は稀であり許容する
- **途中結果と確定結果の表記が違う**: 先頭一致しないため両方登録される。D4（add-quadmemo-quadrant-ui）の割り切りの範囲
- **書き戻しの構造が iOS の更新で変わる**: 先頭一致しなくなれば従来の二重登録に戻るだけで、それ以上に悪化はしない
