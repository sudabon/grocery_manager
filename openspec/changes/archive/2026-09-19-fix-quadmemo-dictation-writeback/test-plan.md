# Test Plan

specs/ 配下の全シナリオ（memo-board 4 件）を、E2E で検証可能な観点へ翻訳したもの。
受け入れ基準の原本は spec のシナリオであり、本ファイルで新しい仕様は定義しない。

前提:

- OS のディクテーションは E2E から起動できない。書き戻しは「空の入力欄に対する、選択範囲なしの `insertText` による一括挿入」なので、E2E では `fill` で同じ形の入力を与えて再現する（design.md - Context / D3）
- 辞書は空（`seed:empty-board`）。すべてのチップは Q4 に未分類で置かれる
- chromium と mobile-safari の両方で実行する（書き戻しが起きるのは iOS だが、コミット制御自体は共通）

### 異常系・境界の検討結果

- **異常系**: 書き戻しが「コミット済みと同一」（TP-001）と「続きあり」（TP-002）の両方を含めた。先頭が一致するだけの新しい入力を削らないこと（TP-003 / TP-004）を含めた
- **境界値**: 書き戻しが空・コミット済み文字列が空（コミット前の書き戻しはあり得ない）はユニットへ委譲
- **多重送信**: 手動コミットとタイマーの競合は既存 `add-quadmemo-quadrant-ui` の観点で担保済み。手動コミット後の書き戻しはユニットで固定する
- **空データ**: 該当なし（辞書が空でも経路は同じ）
- **権限境界**: 該当なし

## E2E対象外(委譲先と理由)

| シナリオ | 委譲先 | 理由 |
|---------|--------|------|
| 途中結果の範囲置換の後は新しい入力として扱う（要件 2 段落目） | Vitest（`InputBar` の単体テスト） | Playwright の `fill` は空でない入力欄に対して全選択→挿入になるため、範囲置換を「書き戻し」と分けて狙って発生させられない。単体テストで選択範囲あり／なしの `beforeinput` を与えて固定する |
| 手動コミットの後の書き戻し | Vitest（`useCommitController` の単体テスト） | 自動コミットと同じ経路。E2E では TP-001 / TP-002 の自動コミット側で代表させる |
| 実機の iOS ディクテーションでの書き戻し | 実機手動検証（design.md - D3） | OS の機能で E2E から起動できない。修正後の実機ログで `COMMIT "牛乳"` → `COMMIT "、卵"` を確認済み |
