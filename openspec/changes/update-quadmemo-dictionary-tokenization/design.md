## Context

分割は `src/core/tokenize.ts` の 1 関数に閉じている。`Intl.Segmenter('ja', { granularity: 'word' })` の結果から `isWordLike` なセグメントだけを取り出し、文字列配列として返す。この時点で「どこに区切り（空白・句読点）があったか」は捨てられている。

`src/core/commitText.ts` は `tokenize(text)` の結果を先頭 50 件へ切り詰め、トークンごとに `resolvePlacement` → `classify` を呼ぶ。辞書は `useAppStore` が `buildNormalizedDicts` で作った `NormalizedDicts`（正規化済みエントリの完全一致 Map と全エントリ配列）として保持されている。

分割を辞書に従わせる動機は proposal.md を参照。

## Goals / Non-Goals

**Goals:**

- 利用者が辞書へ登録した語が、分割で割れないこと
- 結合の判定が既存の正規化・完全一致と同じ規則で行われ、規則が二重にならないこと
- 辞書に登録していない語の分割結果が、従来と 1 トークンも変わらないこと

**Non-Goals:**

- 形態素解析器や辞書データの同梱。分割の精度そのものを上げることは狙わない
- 複合語専用の辞書・設定・UI の追加
- 既に保存されているチップの再分割

## Decisions

### D1: 結合は分割の後段に置き、既存の `NormalizedDicts` を再利用する

`buildNormalizedDicts` が返す `exact: Map<string, Entry[]>` は正規化済みエントリの完全一致索引そのものなので、結合の判定は `exact.has(normalize(連結文字列))` で済む。辞書用の別インデックス（トライ木など）は作らない。

探索の打ち切りに使うため、`NormalizedDicts` へ `maxEntryLength`（正規化後の最長エントリ長、エントリが無ければ 0）を追加する。0 のときは結合を一切試みない。

代替として、生テキストに対して辞書の最長一致スキャンを行う方式も検討したが採らない。正規化は NFKC を含むため文字数が保存されず（半角カナの濁点、`㌢` などの互換文字）、正規化後の一致位置から原文の範囲を復元できない。セグメント単位で連結してから正規化すれば、原文の範囲は常にセグメント境界に一致する。

### D2: 結合の責務は `tokenize` が持つ

区切りを跨がない判定には、捨てられてしまう「非 word-like セグメントの位置」が要る。呼び出し側で結合しようとすると境界情報を別途受け渡すことになるため、`tokenize` の内部に閉じる。

シグネチャは `tokenize(text: string, dicts?: NormalizedDicts): string[]` とし、辞書を渡さない場合は現在と同じ結果を返す。`tokenize` は `classify.ts` から型のみを取り込む（実行時の依存は増えない）。

内部では、word-like セグメントが連続する範囲を「ラン」として扱い、ランごとに結合する。フォールバック経路（`Intl.Segmenter` 非対応）は、区切りで割った各塊を長さ 1 のランとして同じ処理へ通す。この経路では結合が起きないが、分岐を増やさないために経路は共通にする。

### D3: 結合は左から順の貪欲法、同じ開始位置では最長一致

```
i = 0 のランの位置から、連結長が maxEntryLength を超えるまで k を伸ばし、
exact.has(normalize(連結)) となった最大の k を採用する。
一致が無ければ k = 1（そのセグメント 1 つ）を出力し、次の位置へ進む。
```

計算量はラン長 × `maxEntryLength` に収まり、辞書のエントリ数には比例しない。

「最長一致を全体最適で解く」方式（分割の全探索）は採らない。買い出しメモの入力長では差が出ず、結果の説明も難しくなる。左から最長で貪欲に取る規則は、利用者へ「先に出てきた語から順に長いほうが採られる」と説明できる。

### D4: 結合の判定に設定「部分一致を許可」を使わない

部分一致で結合すると、原文に無い語をチップにすることになる（`鶏むね` を `鶏むね肉` のチップにするなど）。結合の根拠は「原文の並びが辞書の語と一致すること」に限る。

部分一致の設定は従来どおり、結合後のトークンを `classify` へ渡す段階でだけ効く。

### D5: 各種上限・重複抑止は結合後のトークンへ適用する

`commitText` は `tokenize(text, normalizedDicts)` の結果に対して従来どおり `slice(0, 50)` し、`addChips` へ渡す。結合はトークン数を減らす方向にしか働かないため、50 件上限・象限ごとの 100 文字上限（連結時の改行が減る）はいずれも緩和方向で、新たに拒否される入力は生じない。重複抑止は結合後のトークンの正規化文字列で判定される。

### D6: 辞書の更新は次のコミットから効く

結合は `useAppStore` の `normalizedDicts` を参照する。辞書の編集・インポート時に `buildNormalizedDicts` が呼び直される既存の経路をそのまま使うため、追加の同期処理は要らない。すでに生成されたチップは再分割しない。

### D7: 既存の登録ヘルプを結合の動作に合わせる

実装レビューで、辞書画面と `dictionary-management` の既存仕様に「分割後の単位で登録」と案内する旧制約が残っていることを確認した。1 つのチップにしたい語全体を登録し、空白や句読点を挟んだ語は結合されない旨へ変更する。画面構造は変えず、既存の登録ヘルプ E2E の期待値を更新する。

## Risks / Trade-offs

- **意図しない結合** → 結合は「原文の並びが辞書エントリと完全一致」した場合に限られ、できあがるトークンは必ず利用者自身が登録した語になる。2 トークン以上でなければ結合は起きないため、1 文字エントリの登録で周囲が巻き込まれることもない
- **貪欲法が最適な分割を逃す**（`AB` と `BC` が登録され入力が `ABC` のとき、`AB` + `C` になる） → 説明可能な規則を優先する。必要になれば、そのときに全探索へ寄せる
- **辞書が大きいと結合の探索が伸びる** → `maxEntryLength` で打ち切るため、伸びるのは「最長エントリが長い」場合だけ。エントリ数には比例しない
- **既存 E2E への影響** → 初期辞書・既存 fixture のエントリはいずれも分かち書きで割れない語なので、結合は発生せず結果は変わらない。回帰は全件実行で確認する
- **`tokenize` の引数追加** → 既存の呼び出し箇所は `commitText` のみ。任意引数にすることで既存の単体テストも修正不要

## Migration Plan

データ移行なし。IndexedDB のスキーマもエクスポート形式も変わらない。ロールバックは `commitText` から辞書の受け渡しを外すだけで、保存済みデータには影響しない。
