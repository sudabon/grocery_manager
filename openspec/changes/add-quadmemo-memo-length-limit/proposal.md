## Why

象限に入るチップの総量に上限が無いため、共有画像（`board-image-share`）の高さがチップ件数と本文長に比例して無制限に伸びる。伸びた先でブラウザのキャンバス上限を超えると、実測で Chromium は例外を投げずに `"data:,"` を返し（高さ 65,536px 以上）、iOS Safari は面積上限（約 16.7M px）に達する。現在は 0 バイト PNG の共有を `dataUrlToFile` のガードで止めているが、利用者に出るのは「画像を作成できませんでした。もう一度お試しください。」であり、再試行しても決定的に失敗する誤った案内になっている。

本アプリは 1 象限あたりのメモ量が実運用で 100 文字に収まる使い方をしている。この量を仕様として明示し入力時に守れば、画像の高さが構造的に有界になり、上限超過という失敗モード自体が消える。あわせて、画面上でも 1 象限に入る量が予測可能になる。

## What Changes

- 1 象限あたりのメモ量に上限を設ける（**BREAKING**: 上限に達した象限へは追加できなくなる）
  - 上限は、象限内のチップ本文を改行 1 つで連結した文字数が **100 文字**（連結に使う改行も文字数に含める）
  - 上限は象限ごとに独立して数える
- 上限を超える追加・編集・移動を拒否し、利用者へ通知する
  - コミットで複数チップが生成される場合は、上限に収まる分まで登録して残りを通知する（既存の「1 回のコミットで 50 件超は先頭 50 件のみ」と同じ部分登録の扱いに揃える）
  - チップの編集で上限を超える場合は編集を適用しない
  - 別象限への移動で移動先が上限を超える場合は移動しない
- 象限ごとの残り文字数を入力時に把握できるようにする
- インポートにも100文字上限を適用する。既存 ID と入力内の重複を除外して既存メモと統合した結果、いずれかの象限が超過する場合はメモ・辞書・設定を一切変更せず拒否する

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `memo-board`: 「コミット結果の境界処理」に象限ごとの文字数上限による部分登録を加える。「チップの操作」に、編集・移動が上限で拒否される振る舞いを加える
- `data-portability`: 全データのインポートも統合後の100文字上限を検証し、超過時は全データを変更せず拒否することを要求に加える

## Impact

- `src/core/commitText.ts`: トークンから生成するチップを、象限ごとの残り容量で絞る
- `src/store/useAppStore.ts`: `addChips` / `editChip` / `moveChip` に上限判定を入れる。`importData` と repository のインポートにも上限判定を適用
- `src/components/InputBar.tsx` または `src/components/Quadrant.tsx`: 残り文字数の提示
- `src/core/boardImage.ts`: 通常の入力では1文字チップ50個で連結99文字となり、全象限がその状態でも canvas 高さは8,266px（面積約8.9M px）に収まる。画像生成自体は変更せず、この境界をユニットテストで固定する
- `src/pages/MemoPage.tsx`: 上限超過の通知（既存トーストを使う）
- E2E: `add-quadmemo-quadrant-ui`（コミットの境界・チップ操作）と `add-quadmemo-board-image-share`（画像高さ）の観点を維持し、上限内のテストデータへ追随させる

## 記録した前提

- 「100 文字（改行込み）」の数え方は、象限内のチップ本文を改行 1 つで連結した文字列の長さと解釈した。チップ N 個なら「各本文の合計 + (N - 1)」になる。共有画像でチップが縦に並ぶ見え方に対応する数え方である
- 上限に達したときの扱いは、既存の 50 件上限と同じ「入るところまで入れて通知する」部分登録に揃えた。コミット全体を拒否する案は、既存の境界処理と挙動が食い違うため採らない
