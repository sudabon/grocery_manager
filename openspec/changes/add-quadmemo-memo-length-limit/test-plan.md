# Test Plan

specs/ 配下の全シナリオ（memo-board 13 件・data-portability 5 件）を、E2E で検証可能な観点へ翻訳したもの。
受け入れ基準の原本は spec のシナリオであり、本ファイルで新しい仕様は定義しない。

前提:

- 部分登録の通知は「一部のみ登録しました。」、追加・編集・移動の拒否は「象限の100文字上限を超えるため登録できません。」を含む。見出しは件数に代えて「残り○文字」を表示する。

- 上限は「象限内のチップ本文を改行 1 つで連結した長さが 100 文字以下」（design.md - D1）
- 上限に達した状態・残り容量が少ない状態を作るための新規シードが必要（`seed:quadrant-near-limit` / `seed:quadrant-at-limit`）
- インポートが統合後100文字を超える内容を全体拒否することの検証には、上限超過のメモを含む固定ファイルが必要（`files/over-limit.json`）
- 既存の 50 件上限との合流（どちらで絞られたかを区別しない）は design.md - D3 の判断であり、E2E では「一部のみ登録された」ことだけを見る

### 異常系・境界の検討結果

- **異常系**: 上限による拒否（TP-002 / TP-003 / TP-004）と部分登録（TP-001 / TP-008）を含めた
- **境界値**: ちょうど 100 文字で収まる場合と 101 文字で拒否される場合の境界は、数え方（連結長）の検証としてユニットへ委譲する（下表）
- **多重送信**: 上限に達した象限へのコミットを連打しても増えないことは TP-002 が 1 回の操作で担保する。連打を独立観点にはしない
- **空データ**: 空コミット（TP-007）と、上限に達していない空の象限への追加（TP-005）で確認する
- **権限境界**: 該当なし

## E2E対象外(委譲先と理由)

| シナリオ | 委譲先 | 理由 |
|---------|--------|------|
| 象限ごとのメモ量の上限 / 数え方が「改行 1 つで連結した長さ」であること | Vitest（`quadrantLength` の単体テスト） | ちょうど 100 / 101 文字の境界、チップ 1 個・0 個、改行を含む本文などの組み合わせは純粋関数で網羅するのが適切。E2E で境界値を並べるとテストが増えるだけで観測できる事実は増えない |
| 50 件上限と文字数上限の絞り込み順序 | Vitest（`commitText` の単体テスト） | 内部の処理順序であり、利用者から見える結果（一部のみ登録＋通知）は TP-008 と同一。design.md - D3 で「通知を区別しない」と決めたため E2E では判別しない |
| チップの操作 / アクションシートで現在の象限が選べない | 既存 `add-quadmemo-quadrant-ui` の観点 | 本 change で振る舞いが変わらないため、既存観点をそのまま活かす |
| チップの操作 / チップを削除する、編集で空文字にするとチップが削除される | 既存 `add-quadmemo-quadrant-ui` の観点 | 削除は上限を減らす方向で、本 change で振る舞いが変わらない |
| 全データのエクスポートとインポート / 版数拒否・識別子衝突・上書き確認の中止 | 既存 `add-quadmemo-dictionaries` の観点 | 本 change で振る舞いが変わらない |
| 共有画像の高さが上限によって有界になること | Vitest（`boardImageFile` の単体テスト） | 最悪ケース（1 文字チップ 50 個）の canvas 高さを単体で固定する。PNG のピクセル検証は `board-image-share` design - D5 と同じく E2E 対象外 |
