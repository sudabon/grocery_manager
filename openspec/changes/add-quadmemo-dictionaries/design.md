## Context

`add-quadmemo-classification` により、IndexedDB（`memos` / `dictionaries` / `settings`）とリポジトリ層、正規化済み辞書キャッシュ、設定値の読み取りが揃っている。辞書編集画面・設定画面は `add-quadmemo-quadrant-ui` で作った「遷移先の骨組み」のままで中身が無い。

動機は proposal.md - Why を参照。要求の原本は specs/ 配下の 3 つの spec。データ形式は仕様書 §8.3、画面仕様は §5.2 / §5.3。

## Goals / Non-Goals

**Goals:**

- 「辞書は一括編集して明示保存」「設定は 1 項目ずつ即時反映」という 2 つの編集モデルを、利用者に迷わせない形で作り分ける
- インポートを「検証してから適用、失敗時は完全に無変更」に統一し、バックアップからの復元でデータを壊さない
- エクスポートを実用的なバックアップ手段にする（iOS の共有シートで他アプリへ渡せる）

**Non-Goals:**

- 既存チップの再分類（仕様書 §5.2 のとおり行わない。spec で明文化した）
- 辞書のクラウド同期・複数プロファイル
- Service Worker の更新状態表示（`add-quadmemo-pwa-offline` で設定画面へ追加する）
- インポートのマージ戦略の高度化（メモは ID 衝突をスキップするだけ。差分マージはしない）

## Decisions

### D1: 辞書は「テキストエリア + 明示保存」、設定は「即時保存」

- **辞書**: 単語リストは改行区切りのテキストエリアで編集し、保存ボタンで確定する。理由は (a) 仕様書 §5.2 が 1 行 1 語のテキストエリア編集を指定している、(b) 編集途中の不完全な行を分類へ流したくない、(c) 正規化重複除去は「保存時に一括で行う」方が結果を説明しやすい
- **設定**: 各コントロールの変更で即時保存する。項目が互いに独立しており、保存ボタンを挟む意味がない
- **非対称であることを UI で示す**: 辞書編集画面には保存ボタンと未保存インジケータを置き、設定画面には保存ボタンを置かない

### D2: 保存時の整形は core 層の純粋関数

```ts
// src/core/dictEntries.ts
sanitizeEntries(rawText: string): string[]   // 行分割 → trim → 空行除去 → 正規化重複除去（先着優先）
```

- 重複除去は **先に現れた表記を残す**（後続の同一正規化エントリを捨てる）。利用者が上に書いた表記が保存されるので予測しやすい
- 正規化は `src/core/normalize.ts` を再利用する。整形と分類で同じ正規化を使うことが重複判定の一貫性の前提

### D3: 辞書保存後に正規化キャッシュを作り直し、既存チップには触らない

保存トランザクション成功後に `buildNormalizedDicts()` を呼び直してストアのキャッシュを差し替える。`memos` ストアへは一切書き込まない。これにより spec の「辞書変更時に既存チップを再分類しない」が実装構造として保証される。

### D4: インポートは「検証 → 全件通過 → 1 トランザクションで適用」

```
parse(JSON) → validate(型ガード) → confirm(上書き対象がある場合) → apply(単一トランザクション)
                    │
                    └ 失敗 → エラー表示のみ。DB へは触らない
```

- **バリデーションは手書きの型ガード**（`src/core/portability.ts`）。仕様書 §4 の「ライブラリ依存は最小に」に従い zod 等は入れない。検証項目は `schemaVersion` / `dictionaries` の 4 象限の存在と型 / `memos` 各要素の必須フィールドと `quadrant` の値域 / `settings` の型と範囲
- **代替案**: 部分的に適用して不正要素だけ捨てる（「何が入ったか分からない」状態を生むため採らない。ただしメモの ID 衝突スキップは仕様書 §8.3 が明示しているので例外）
- 適用は `memos` / `dictionaries` / `settings` を 1 つの `readwrite` トランザクションで書き、途中失敗時は自動でロールバックされる

### D5: エクスポートは Web Share API 優先、`navigator.canShare({ files })` で判定

- `navigator.canShare?.({ files: [file] })` が真なら `navigator.share({ files })`、偽または例外なら `<a download>` でダウンロード
- **理由**: iOS の standalone PWA ではダウンロードの扱いが分かりにくく、共有シート経由（ファイルアプリ・メール等へ保存）が実用的。一方でデスクトップや共有非対応環境ではダウンロードが必要
- **注意**: `navigator.share` はユーザージェスチャ内から呼ぶ必要がある。エクスポート用の JSON 生成は同期的に行い、`await` を挟まずに `share()` を呼ぶ
- ファイル名は `quadmemo-export-<日付>.json` / `quadmemo-dictionaries-<日付>.json`

### D6: 確認ダイアログは `ChipActionSheet` と同じ `<dialog showModal>` 基盤

`src/components/ConfirmDialog.tsx` を追加し、メモ全削除の 2 段階確認と、インポートの上書き確認に使う。ブラウザネイティブの `confirm()` / `alert()` は使わない（`add-quadmemo-quadrant-ui` design - D8 と同じ理由に加え、自動テストがブロックされるため）。

- メモ全削除の 2 段階は「削除しますか」→「本当に削除しますか（元に戻せません）」の 2 連ダイアログとし、2 段目の承認ボタンは破壊的操作として明示する

### D7: 自動コミット待機時間はスライダー + 値のクランプ

`<input type="range" min=500 max=5000 step=100>` を使い、保存前に必ず範囲内へクランプする。range 入力自体が範囲を強制するが、インポート経路からも同じクランプを通す（spec の「範囲外の値は保存されない」はインポートにも及ぶ）。

### D8: 設定画面のアプリバージョンはビルド時に埋め込む

`import.meta.env` 経由でビルド時のバージョン文字列（`package.json` の `version`）を埋め込む。実行時に `package.json` を読むことはできないため。

### D9: E2E のファイル入出力

- **エクスポート**: ダウンロードイベントを捕捉して内容を読む（`env:no-web-share` fixture で共有機能を無効化し、ダウンロード経路に固定する）
- **共有経路**: `env:web-share-stub` fixture で `navigator.share` / `canShare` をスタブし、呼び出しと渡されたファイル名を記録する
- **インポート**: `tests/e2e/fixtures/files/` に固定ファイル（正常・壊れた JSON・版数不一致・ID 衝突あり）を置き、ファイル選択へ渡す
- ラウンドトリップ（エクスポート → 全削除 → インポート）は 1 テストで完結させ、テスト間で状態を共有しない

## Risks / Trade-offs

- **インポートによるデータ喪失**（最も重い） → D4 の「検証してから単一トランザクションで適用」＋辞書・設定の上書き確認。メモは追加のみで既存を消さない。E2E で「不正インポート後に無変更」「確認中止で無変更」を検証する
- **メモ全削除の誤操作** → 2 段階確認と破壊的操作の明示。E2E で中止経路を検証する
- **辞書の重複除去で利用者の表記が消える**（例: 「レビュー」と「れびゅー」の両方を登録したいのに 1 件になる） → 仕様書 §7.2 の「正規化により実質同一になる」仕様どおりの挙動。辞書編集画面のヘルプで「正規化して同じになる表記は 1 件に統合される」ことを明記する
- **`navigator.share` の非同期呼び出しでユーザージェスチャが切れ、iOS で共有シートが出ない** → D5 のとおり同期的に組み立てて呼ぶ。実機確認を受け入れタスクに置く
- **大量エントリ（数千語）の保存時に正規化キャッシュ再構築が重い** → 保存は明示操作なので待たせても実害が小さい。コミットのたびに再構築しない構造（D3）が効いている
- **設定の即時保存で書き込みが頻発する**（スライダー操作中） → スライダーは変更確定（`change`）で保存し、ドラッグ中（`input`）は保存しない

## Migration Plan

新規機能のため移行なし。エクスポート形式は `schemaVersion: 1` として固定し、将来の形式変更時はこの値で分岐する。
